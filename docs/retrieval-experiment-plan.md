# 検索層改善の実験計画: Dense / Sparse / Query Expansion の 2×2 要因実験

作成: 2026-07-16（ベースライン再計測 2026-07-19）。ベースライン数値は `data/eval/scores_20260719.json`（eval set 66問）。
統計手法・指標設計の背景は [experiment-design.md](experiment-design.md) を参照。

---

## 1. 背景と目的

SoundQuest 音楽理論コーパス（162記事、構造ベースchunking、2,355チャンク）に対する
RAG検索層は、現在 BGE-M3 の dense ベクトル（1024次元）のみで検索している。
BGE-M3 は sparse（語彙重み）も同時に出力できるモデルだが、ingest 時に捨てている。

評価基盤の刷新（Phase 5）で、検索層の弱点が2つ定量化された:

1. **表記ゆれ**: 「5-1」「V-I」「ドミナントモーション」が同じ概念を指すが、dense 検索は
   記号トークンの一致に弱い（silver の「5-1と4-1の違い」型の質問が長期未解決）。
2. **AND質問（複数記事の統合が必要な比較質問）**: recall@5 0.352 / strict_hit 0.111（n=27）。

本実験の目的は、**(a) sparse の追加と (b) query expansion がそれぞれ・組み合わせで
検索品質をどれだけ改善するかを、要因を分離して測る**こと。

### スコープ外（今回やらないこと）

- **クエリ分解→並列検索→マージ（AND質問対策の本命）**: **Phase 2** として別実験。
  理由: AND の失敗は「1本のクエリベクトルは2つのトピックの近傍に同時にいられない」
  という構造的天井（下記 §2）であり、sparse/QE では原理的に直らない。
  今回の実験で AND 層が動かなくても想定内であり、失敗ではない。
- **Adaptive RAG / Router-based RAG**: **Phase 3**（§10 に設計を先行記載）。
  ルーターは検索そのものを改善しない「振り分け層」であり、強みの異なる
  パイプラインが複数揃って初めて価値が出る。Phase 1・2 の後に置く。
- **graph RAG**: ①〜③の結果を見てから判断（構築コストが桁違いのため後回し）。
- **reranker / nDCG**: 上記が済んでから。

## 2. ベースラインと故障診断

### ベースライン（dense only, collection = `music_theory_structure`, n=66, k=5）

| 層 | n | recall@5 | strict_hit | MRR |
| --- | --- | --- | --- | --- |
| **全体** | 66 | **0.599** | **0.500** | **0.562** |
| single（silver） | 20 | 0.850 | 0.850 | 0.800 |
| or | 19 | 0.684 | 0.684 | 0.478 |
| and | 27 | 0.352 | 0.111 | 0.444 |

（source別: forum n=40 recall 0.512 / generated n=6 recall 0.333 / silver n=20 recall 0.850。
generated 6 は §8 度数足場の検証用に追加。fixed collection の同時再計測は
recall 0.571 / strict_hit 0.470 / MRR 0.581 で、structure との差は依然小さい）

### 診断1: AND の失敗は「ランキング」ではなく「構造」

AND 層は recall 0.386 に対し MRR 0.485。つまり**1記事目はおおむね上位2位以内に
見つかるが、2記事目以降が top-5 にほぼ出ない**。1クエリ=1ベクトルである限り、
異なるトピックの記事を同時に上位に出せない。→ 分解検索（Phase 2）の担当。

### 診断2: 表記ゆれは dense の意味近傍の外にある

度数表記（「5-1」等）は自然文との意味類似度が低く、dense 単独では該当記事の
チャンクが上位に来ない。語彙一致（sparse）またはクエリ側の正規化（QE）が必要。

### ケーススタディ: forum_76963（AND, 「1-2と5-6の接続の質感の差」）

埋め込み空間の可視化（`experiments/viz_retrieval.py`、図は
`data/eval/viz/forum_76963_music_theory_structure.png`）と実 cosine 順位:

| 正解記事 | cosine順位 | 状況 |
| --- | --- | --- |
| `nx-2nd` | 20位（top-5の壁 0.644 に対し 0.620、差0.024） | クエリの近傍にいるが、兄弟記事（nx-5th系・音程系）のチャンク約20個に押し出される。**混雑近傍での順位問題** |
| `cst-apply-chordscales` | 100位圏外 | 意味空間の別領域にクラスタ形成。この質問文からは原理的に届かない。**構造的到達不能** |

1つの AND 質問に2つの故障モードが同居している実例。前者は Phase 1（sparse の
語彙一致・将来的には reranker）、後者は Phase 2（分解検索）の守備範囲であり、
**単一の打ち手では AND 質問は救えない**ことを示す。

## 3. 実験条件（2×2 要因計画）

|  | QE なし | QE あり |
| --- | --- | --- |
| **sparse なし** | **[Base]** dense only（測定済み） | **[B]** dense + QE |
| **sparse あり** | **[A]** dense + sparse | **[C]** dense + sparse + QE |

- 4条件を**同一の60問 eval set**で評価し、すべて Base に対する paired difference で見る。
- 要因計画なので以下が分離して主張できる:
  - **sparse の主効果** = A − Base（および C − B）
  - **QE の主効果** = B − Base（および C − A）
  - **相互作用** = (C − Base) − [(A − Base) + (B − Base)]。
    正なら相乗、負なら干渉（例: QE が足した語が sparse の完全一致を薄める）。

### 統制条件（結果を比較可能にするための不変条件）

- chunking: structure（チャンク内容・IDは全条件で同一）
- 埋め込みモデル: BGE-M3（dense ベクトルは Base と bit 同一であること）
- top_k = 5、eval set = `eval_set_merged.json`（60問, frozen）
- 変えるのは「sparse の有無」「QE の有無」の2要因のみ

## 4. 仮説（研究フレーム: 課題 / 仮説 / 根拠 / 結果）

### 条件A: dense + sparse（ハイブリッド検索）

- **課題**: 度数表記・記号トークンの一致に dense が弱い。
- **仮説**: sparse（語彙重み）の追加で表記一致の質問の recall が改善する。
- **根拠**: BGE-M3 は dense/sparse を1パスで出力でき追加コストが最小。
  BM25系の語彙一致が記号・固有語に強いのは IR の定石。クエリ時の追加レイテンシほぼゼロ。
- **結果**: TODO（未計測）

### 条件B: dense + query expansion

- **課題**: 同上（表記ゆれ）＋口語質問の語彙不足。
- **仮説**: 検索前にLLMで質問を書き換え（度数表記の正規化・同義語の付加）ることで
  dense 単独でも正解チャンクに近づく。
- **根拠**: 「5-1」→「V-I ドミナントモーション 正格終止」のような展開は、コーパス側の
  語彙にクエリを寄せる操作であり、埋め込み空間上の距離を直接縮める。
- **トレードオフ**: クエリごとにLLM呼び出し1回（レイテンシ+コスト）が本番経路に乗る。
  同じ課題を狙う条件Aはクエリ時コストゼロなので、**AとBの効果が同等なら A を採用すべき**。
- **結果**: TODO（未計測）

### 条件C: dense + sparse + QE

- **課題**: A・B の効果が独立に足し算されるか、干渉するか不明。
- **仮説**: 相補的（QEが意味側、sparseが語彙側を拾う）なら C が最良になる。
- **根拠**: 干渉の可能性もある（QEが付加した語が sparse の重み分布を薄める等）。
  要因計画だからこそ、この相互作用を数値で答えられる。
- **結果**: TODO（未計測）

## 5. 評価指標と主指標の事前宣言

**p-hacking 防止のため、条件ごとの主指標を着手前にここで宣言する。**
（8個の数字を眺めて動いたものを事後に「効果」と呼ぶことを禁止する）

| 条件 | 主指標（これで採否判断） | 副指標（解釈の補助） |
| --- | --- | --- |
| A (sparse) | **表記ゆれタグ付き質問の recall@5** | 全体 recall@5、MRR |
| B (QE) | 同上 | 同上 ＋ QE後のクエリ文の質的確認 |
| C (両方) | **全体 recall@5** ＋ 相互作用の符号 | 層別すべて |

- **前提タスク**: eval set に `notation_variant`（度数表記・記号ゆれを含む質問）タグを
  付与する（現状 match_type/source/difficulty しか層がないため）。タグ付けは
  質問文に度数・記号表記（例: 数字-数字、ローマ数字、コードシンボル）を含むか
  どうかの機械判定＋人手確認で行い、**実験開始前に freeze する**。
- AND 層の数値も記録するが、今回の条件では動かない見込み（§2 診断1）。
  動いたら儲けもの、動かなくても失敗ではない。
- RAGAS（context_precision）は、retrieval 指標で最良だった条件 vs Base の
  1ペアのみ節目で実行（コール数 = 60問 × 5 × 2条件 = 600、judge費用 $0.1〜0.5 程度）。

## 6. 統計分析計画

[experiment-design.md](experiment-design.md) の方針をそのまま適用する:

1. すべての比較は **paired difference**（同一質問での差分）。`experiments/paired_diff.py` を使用。
2. 平均差の **bootstrap 95%CI**（10,000リサンプル）と **Wilcoxon 符号順位検定** を報告。
3. **match&#95;type / notation&#95;variant / source で層別**（全体平均は弱点を隠す）。
4. 効果の解釈: CI が 0 をまたがない場合のみ「改善」と呼ぶ。
   またぐ場合は「n=60 では検出できない差」と正直に書く。
5. 期待される検出力: 表記ゆれ層を狙い撃つ介入は、当該層で大きな効果
   （例: recall 0.4 → 0.7）を狙うため、層の n が 15〜20 程度でも検出可能な見込み。
   小さな全体効果を大きな n で拾う設計はとらない。

## 7. 実装計画

### 7.1 ハイブリッド collection（条件A・Cで使用）

- 新 collection `music_theory_hybrid` を作成（本番 `music_theory_structure` は不変。
  実験隔離の原則）。
- BGE-M3 で dense + sparse（lexical weights）を1パスで出力し、Qdrant の
  named vectors + sparse index に格納。チャンク内容・point ID（uuid5）は structure と同一。
- **検証**: ランダムに数点サンプリングし、dense ベクトルが `music_theory_structure` と
  一致することを確認（一致しなければ「sparseの効果」が分離できない）。
- 融合: Qdrant Query API の **RRF**（Reciprocal Rank Fusion）を第一候補とする。
  重み付き線形結合は感度分析として余力があれば。
- **運用注意（8GB機）**: 2,355チャンクの再埋め込みが必要。BGE-M3 embed と
  Docker/Qdrant の同時実行はスワップ死の前科があるため、embed（Docker停止中）→
  upsert（Docker起動後）を時間分離する。

### 7.2 Query expansion（条件B・Cで使用）

- 検索前に LLM 1回で質問を書き換える。モデル: `gemini-3.1-flash-lite`
  （実測 0.7s / 呼び出し、コスト無視できる規模）。
- プロンプト方針: 度数表記の正規化（「5-1」→「V I」等）＋ 音楽理論用語の同義展開。
  **元の質問文は保持し、展開語を追記する形**（rewrite ではなく expansion。
  元の語を消すと sparse の一致まで壊すリスクがあるため）。
- **再現性**: 展開後のクエリ文を per-question 結果（scores JSON）に必ず保存する。
  LLM は確率的なので、保存がないと後から結果を解釈できない。

### 7.3 評価の実行

- `experiments/evaluation.py` は collection 名で切り替わるため、条件A用は
  COLLECTIONS に `hybrid` を追加。QE は evaluation 側にフラグ（env）を追加し、
  retrieve 前に展開を挟む。
- 実験条件スナップショット（QE使用有無・展開モデル名・融合方式）を
  スコア JSON に含める。

## 8. 結果の解釈マトリクス（事前に決めておく）

| 観測パターン | 解釈 | 次のアクション |
| --- | --- | --- |
| A ↑, B ↑, C ≈ A+B | 両者は相補的 | C を本番採用候補に |
| A ↑, B ↑, C < A+B | 干渉（QEがsparse一致を薄める等） | C の融合重み/QEプロンプトを調整 or 単独採用 |
| A ↑, B ≈ 0 | 語彙一致で足りる。QE不要 | **A を採用**（クエリ時コストゼロで優位） |
| A ≈ 0, B ↑ | 表記ゆれは意味側の問題だった | B 採用。sparse の実装は撤去可 |
| A ≈ 0, B ≈ 0 | 表記ゆれ仮説自体が誤り | per-question 分析で故障モードを再診断 |
| AND 層が動く | 想定外の儲けもの | 動いた質問を個別に読んで機構を特定 |

## 9. 実施順序

1. eval set に `notation_variant` タグ付与 → freeze（§5 前提タスク）
2. RAGAS context_precision のベースライン取得（Base、60問、300コール）
3. 条件A: hybrid collection 構築 → retrieval 評価 → paired diff
4. 条件B: QE 実装 → retrieval 評価 → paired diff
5. 条件C: 組み合わせ → retrieval 評価 → paired diff ＋ 相互作用の算出
6. 最良条件 vs Base で RAGAS context_precision の paired diff
7. 結果を本ドキュメントの「結果: TODO」に記入し、採否判断
8. **Phase 2**: クエリ分解→並列検索→マージで AND 層に挑む
9. **Phase 3**: Adaptive Router（§10）。分解パイプラインが AND 層で効果を示した場合のみ

## 10. Phase 3: Adaptive RAG / Router-based RAG（設計の先行記載）

### 位置づけ

ルーターは**検索改善手法ではなくオーケストレーション層**。質問のタイプを判定し、
タイプごとに最適なパイプラインへ振り分ける:

```
質問 → ルーター → single/or 系 → 通常検索（Phase 1 の最良条件）
              └→ and 系（比較・複数概念） → 分解→並列検索→マージ（Phase 2）
```

（古典的 Adaptive-RAG（Jeong+ 2024）には「検索なし」分岐もあるが、本システムは
出典提示が必須要件のため retrieval-free 分岐は採用しない）

### 動機（診断データより）

- single 層は dense のみで recall 0.85 と健康 → 全質問への分解適用は
  約7割の質問にとって純粋な無駄（LLMコール数倍増・レイテンシ増）。
- ルーターの価値 = 「品質の底上げ」ではなく **「必要な質問にだけ高コストな
  処理を出す」コスト/品質のパレート改善**。

### 本プロジェクト固有の強み: ルーター評価がタダでできる

eval set の `match_type`（single/or/and）は「どのパイプラインに行くべきか」の
**正解ラベルそのもの**。したがって:

1. **ルーティング精度**が直接測れる（ルーター判定 vs match_type、60問）。
   特に少数クラス（and, n=22）の再現率を重視する（and の取りこぼし＝
   分解が必要な質問に通常検索を出す＝Phase 2 の効果を捨てる誤り）。
2. **オラクルルーター**（match_type ラベル通りに振り分け）の成績を先に計算できる。
   これが「ルーティングが完璧な場合の上限」であり、**ルーター本体を実装する前に
   投資判断ができる**。オラクル ≈ 全問分解 なら、ルーターの価値はコスト削減のみ。

### 実験条件（Phase 2 完了後）

| 条件 | 内容 |
| --- | --- |
| R-Base | Phase 1 最良条件を全質問に適用 |
| R-All | 分解を全質問に適用 |
| R-Oracle | match_type ラベルで振り分け（上限の測定） |
| R-Router | 実ルーターで振り分け |

- 主指標: 全体 recall@5（R-Router vs R-Base の paired diff）＋ ルーティング精度
  （and クラスの precision/recall）＋ 1問あたり平均LLMコール数（コスト軸）。
- 採否判断: R-Router が R-Base を上回り、かつ R-All 比でコールを有意に削減し、
  R-Oracle との差が小さいこと（差が大きい＝ルーター精度がボトルネック）。

### ルーター実装の候補（軽い順に試す）

1. **ルールベース**: 比較マーカーの正規表現（「違い」「どっち」「比較」「〜と〜」等）。
   日本語の比較質問は表層パターンが強く、ゼロコスト・決定的・説明可能。
2. **LLM分類**（flash-lite、実測0.7s）: few-shot で single/and を判定。
   ルール版の精度が不足した場合のみ。
3. 埋め込み分類器等の学習ベースは n=60 では過学習リスクが高く、当面採用しない。

## 11. この実験で言えるようになること（ポートフォリオ観点）

- 「診断（表記ゆれ・AND の構造的天井）→ 故障モードに対応する最小の打ち手 →
  要因を分離した測定 → CI 付きの採否判断」という一連の流れ。
- 全体平均ではなく層別で効果を示す（表記ゆれ層に効いた/効かなかった、が主張の単位）。
- 「有意差なし」も結論として報告する（fixed vs structure, n=60 の前例と同じ誠実さ）。
- Phase 3 まで進めば「クエリタイプごとに最適パイプラインを選ぶ Adaptive RAG を、
  正解ラベル付きでルーティング精度まで含めて評価した」という、単なる手法の寄せ集め
  ではないシステム設計の主張ができる（オラクル上限との比較込み）。
